Implementing DragGAN using JAX & Flax NNX

Jul 10, 2026

I have never used the JAX framework before but wanted to learn it. So I decided to read the DragGAN paper and implement it using JAX and Flax NNX. This post will cover a high-level overview of DragGAN, things I found interesting about the JAX framework, analysis of my implementation, experiments and corresponding findings. I will not cover implementation details here, you can go through the repository, and my thought dump for that

Understanding DragGAN

(For those already familiar with this topic, feel free to skip this section)

You can imagine DragGAN as a tool that lets you use your cursor to drag one point in an image to the other, and when I say “drag,” I don’t mean that wonky Photoshop-type of dragging that stretches/compresses the subject. I mean a semantically preserved, faithful manipulation of the image. For example, let’s say we have a smiling kid. If I don’t want the kid to smile anymore, I could tell him Santa is not real and make fun of his hair. However, social norms say such behaviour is wrong. So instead I would take a photo of the child’s face (with the parent’s consent ofcourse), go back to my laptop, upload the photo, and drag certain points like so:

And viola! A totally socially acceptable way to make a kid’s smile disappear. Jokes aside, DragGAN allows you to perform many such manipulations; closing the eyes in image of a human face, changing the size of the wheel in the image of a car; you could perform endless transformations at a high semantic level. We will henceforth refer to these transformations as pointwise manipulations. Now how does DragGAN achieve this? The authors have already given a detailed and technical explanation on how it is able to do this, but I like to think about it through a more high-level perspective because, to me, DragGAN elegantly utilises one of my favourite concepts in machine learning, the manifold hypothesis.

How DragGAN uses the manifold

The manifold hypothesis states that almost all naturally occuring high-dimensional datasets lie along low-dimensional manifolds. As a result of this, high-dimensional data points can be faithfully represented (and explained) by a lower dimensional structure, allowing ML algorithms to learn abstract relevant features from high-dimensional data. In our case, the dataset is all naturally occuring images. As per the manifold hypothesis, we can represent every naturally occurring image using a low dimensional structure. StyleGAN already does this, it samples from a normal distribution z, passes it through the mapping network to get the disentangled latent code w, and then passes that through a generator to get the image (For a quick primer on StyleGAN you can go through this article). This disentangled latent code w is exactly the low-dimensional structure that represents high quality images. (An argument can be made that it is in fact z and not w that is a representation of the image. This claim could be valid, but assuming a bijective mapping between Z and W, this technicality does not really change anything).

I like to thing of the disentangled latent code as the coordinates of that specific image on the manifold. Changing this coordinate in a specific direction changes a particular attribute of the image. For example, I have an image of a bearded man and its corresponding disentangled latent code (w code for shorthand), if I drag the w code along a certain direction on the manifold, the man’s beard in the image could become denser and if I drag it in the opposite direction along the same axis, the beard could become sparser. However, I need to be careful to stay on the manifold, because if I go out, the image would completely lose structure and essentialy become noise.

DragGAN does exactly this. Through numerous small precise updates to the w code, it drags an image across the manifold until it gets to the target image.

If you would like a more detailed explanation of DragGAN, I encourage you to read the paper

JAX

I’ll keep this short. JAX is Google’s recent framework for high-performance array computation. Its enforces the functional programming paradigm, and supports a stack of additional libraries for writing, training and testing machine learning algorithms and large-scale models. It offers enough functionalities to be an enticing alternative to PyTorch, and its interface is one of the most intuitive that I have seen so far.

JAX also offers Flax, a framework for developing ML models, supporting jax operations as well. As JAX enforces functional purity, Flax is a useful tool for implicit state management when working with stateful models.

JAX supports using Just In Time (JIT) compilation to accelerate your code. You can flexibly choose what specific function you want to accelerate using JIT, and while there are limitations on what kind of code you can write for a jitted function, JAX offers multiple workarounds for it. JIT compilation is achieved by tracing the function on first use and optimising it using XLA (Accelerated Linear Algebra).

Implementation experience

The name DragGAN makes you think that implementation consists of writing and training a model, but that is not the case. DraGAN is simply an algorithm that operates on top of the StyleGAN-2 generator, and this algorithm does not update the generator weights, but rather the input to the generator (w_code). Here’s a short version of the algorithm

  1. We get an image along with it’s corresponding w code from StyleGAN
  2. The user picks handle point p and target point t
  3. Using motion supervised patch loss, the w code is changed, so that the resuting image is slightly changed in desired way.
  4. Use point-tracking algorithm to capture the new handle point p
  5. Go to step 3, until the condition of p~=t is satisfied

Implementing this algorithm in JAX was fairly straightforward, you can check my implementation journey here. The jax.numpy module (which is a mirror of the numpy module but JAX compatible) was a huge help in implementing complex mathematical operations and array computations, and I feel like any programmer with some experience in Python would feel familiar with the JAX interface right off the bat.

Even in the case of DragGAN, where the optimisation is for the w_code rather than the weights, writing the optimisation step was simple and uncomplicated. I will admit that I was confused when trying to use the Adam optimizer from Optax module, as Optax implements the state of the optimiser seperately from its structure. However once I understood that, the confusion was quickly cleared up.

Acceleration was easy to implement thanks to the JIT decorators provided by JAX, which allowed me to selectively accelerate any functions, and customize the acceleration parameters as well. All in all, great experience, I cannot give a rating based on one experience, but I look forward to using JAX in future projects.

Results

Implementing it was the easy part; figuring out why I was getting skewed results was more frustrating. I performed multiple experiments on images from multiple datasets, finding several that work and some that don’t. The biggest problems that I noticed amount to the following—

  1. The point-tracking algorithm too often caused the handle point to drift away from that actual feature that it is supposed to be tracking, leading to bad updates
  2. The heuristics given by the authors (Take the 6th block of the generator as the feature block, update only the first 6 layers of W+) don’t seem to apply effectively for every image. While performing an abltaion study, I sometimes noticed that updating only first 4 layers yielded better results, while sometime using the 7th feature block had better success. I suppose it is because specific features are more predominant in specific blocks. As a follow-up, I would like to study the feature maps of StyleGAN-2, and try to determine a way to see which feature is more active in which block.

I first verified that my code was not flawed and not causing this drift, after which I tried various solutions from hyperparameter tuning to modifying the algorithm. The two main things I tried and which failed were:

  1. Giving more preference to the original point and the points around it, to encourage point-tracking to stick close to the original point, and only pick another point if there is a strong likelihood
  2. Updating the reference point on every iteration using an exponential averaging formula.

It turns out this problem is a documented limitation, called ‘ambiguous tracking’, and there have been follow up papers to adress this limitation. One of the papers employed a ‘self-updating reference point’, which was similar to what I tried, but they employed dynamic weights for the exponential averaging. They also restricted the point-tracking algorithm to only search for points in the 1d line connecting the handle point and target point.

I think there might be an easier or more elegant solution to solving point-tracking. The authors had the correct intuition, but this algorithm requires stricter constraints and more robust hyperparameters. Its also a very real possibility that the StyleGAN weights which I used were not upto the mark, although the source I obtained it from, mentioned that they used NVIDIA’s official weights (link).

On the subject of speed, I tested my algorithm on the NVIDIA Tesla T4 GPU, and depending on how far the target point is from the handle point, a drag loop took anwhere from 20 seconds to 5 minutes. To speed it up further, I plan to write kernels for the StyleGAN generator, and I will see how it goes.

Complete miss. Maybe its because I placed the points a little too inside the lips and the algorithm was unable to understand how to move those points outward. So the patch loss is unable to move the lip in that direction, probably because the manifold does not support images of men with wierd smiles, so instead it changes the area around the lips which consequently changes the entire face structure. Notice how each handle point has converged to the target point even if the actual feature is not at the target point. So the w_code changed such that the feature values travelled towards the target point, but the actual feature did not move at all. I actually cannot think of an explanation for this. Point-tracking does not apply a penalty to the w_code, how could the algorithm faithfully nudge the w_code to move the feature from the handle point to the target point, but not affect the feature at all? Is it an absence of stochasticty perhaps? You’ll see that in all the results the face shape, expression, and other features we were not targeting have been changed. It could also be that the point-tracking algorithm is inherently flawed as we discussed, and it was by random chance that it matched a nearest neighbour, but it does not explain how the handle point converged to target point in each case. I did not put any constraints on point-tracking for this experiment.

Conclusion

The main goal of this project was to learn the JAX framework, which I think I have achieved. Ofcourse, ‘knowing’ a framework has a very loose meaning. Obviously I cannot claim knowledge to every method in this framework or even know how the internals work, but I understood the paradigm it utilizes and how to use it effectively, and I’ll learn the rest as I use it more. Coming to the subject of DragGAN, as discussed above there were many things left to be analysed and refined, and there is potential to improve upon the original algorithm. It is also possible that the discrepancies I notices may be due to mistakes in my implementation. If so, please point it out to me. Obviously there is so much more to analyse and so much more to improve, but I wanted to post this article as a milestone, and a reminder of the work yet to be done.
