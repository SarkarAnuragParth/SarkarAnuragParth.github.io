Implementation Experience and Thought Process - DragGAN

Jul 8, 2026

Start

The objective is to code dragGan in JAX. Need to check feasibility, acceleration opportunities, and optimisation potential. Bonus points on developing a kernel for Iris XE.

Understanding of DragGAN

I will now dump my understanding of DragGAN in this section. The functionality provided by DragGAN can be described theoretically, as calling out specific intentional high-level commads to drag the image through the manifold, or transalte it to a specific point on it manifold. The ‘commands’ are given using the mouse cursor to place a point p on the image called the handle point, and a target point t, and have DragGaAN change the image so that p is able to reach t while maintaining visual quality and identity of the image. FOr example, take an image of a human face, if we place the point p on the nose, and t on the right cheek, it will not just drag the nose to that point in a Photoshop kind of way, it will turn the entire face to look in the right direction, making the point p on the nose reach t

Now that I have covered what DragGAN does, lets cover how it does all this. DragGAn is built on top of the StyleGAN. Actually, saying on top of is misleading, its more like DragGAN, utlizes the SyleGAN and its feature maps in every step. Lets break it down.

  1. User uploads an image, and we use an inverter or optimisation algorithms to fetch the w code
  2. The user picks handle point and target point
  3. Using motion supervised patch loss, the w code is changed, so that the resuting image has slightly changed in desired way.
  4. Use the 6th block of StyleGAN to capture the new handle point p, using a nearest neighbours algorithm
  5. Go to 3, until the condition of p~=t is satisfied

The authors mentioned that for the motion supervised patch loss, backpropogation is not taken through one of the terms, essentially detaching it from the computational graph, rendering it a constant.

Implementation Plan

  1. The first thing we require is a trained Style GAN. DragGAN authors used StyeGAN-2 but further variants have come along. I will use StyleGAN-2 to start, and use StyleGAN-3 later if I see any requirement for it.
  2. Once I have a StyleGAN, I will use random z samples to generate images, and try to implement DRagGAN on that. For now, we operate in W space rather than the recommended W+ space.
  3. The flow seems simple enough, generate a z code, use trained StyleGAN to take it to W space, compute feature maps until the 6th block with gradient watch, calculate the loss function, take the gradient of loss function w.r.t W, use Adam optimizer to change the w code slightly, recompute the 6th block, use nearest-neighbours algorith to find new handle point, and repeat the process until |p - t| < d, where d is an arbitary threshold
  4. Once that is done, and the optimal w code has been fetched, generate the new image

Self-constraints

In order to make this a learning experience, I will place the following constraints on myself

  • No looking at the source code
  • Use JAX to implement the model
  • Only use LLMs to search for a certain functionalities and how to use it, or generate snippets of code not related to architecture. Never to write full functions or architectures
  • Debugging should be attempted manually at first, if not successfull after multiple tries, then use LLMs to debug

Analysing feature maps

I wrote a script to take mean of feature maps to produce a grayscale image. A preliminary overview of the mean tells me that the 6th block in ffhq highlights the crude facial features, while the 7th block highlights more fine features. I am thinking of using mode, median, max and min instead of mean to see other statistics of the feature maps. Max and min should most likely lead to completely white and black images respectively, but I am interested to see if any patterns emerge. As they say a fool may try stupid things, but only a greater fool would not try anything at all. … Yes I just made up this quote to justify doing what can only seem to be a useless experiment.

The experiment was in fact not useless, wierdly enough, when I take max/min instead of mean, the resulting gray image still has a striking pattern in the sense that the face and all of its features are clearly visible. Oh one thing I think I forgot to mention is that I have used this script for ffhq dataset, which are 1024x1024 images of faces. Coming back to my point, using what I suspected to be the anomaly statistics led to pretty similar results to the mean. It would be one thing if this only happened in the feature map images where max was taken (henceforth reffered to as the max_image), I would attribute to the max being so much larger that it tipped the mean completely towards itself, but the same phenomenon is observed in min. Another wierd thing that I noticed in these images but I think can be explained, is that the min images are primarily white in color, except for the important face features, which are in black. (If you are not familiar with computer vision and are confused about why I am confused about this, its because in grayscale images, a black pixel has the numerical value of 0 and a white pixel of 255, due to which I was expecting the min_images to be mostly black and max_images to mostly white). I think this is an effect of the normalisation that I am doing to get the image arrays in the range of [0,1]. FOr example, to obtain a max_image, I basically take a feature map stack, I then take the max of a single pixel location across all the feature maps, and make that the value of the single pixel. Doing this gives me a 2 dimensional unnormalised array. So I normalise it to [0,1], uding a process which can be geometrically described as squishing the numbers. You can just look at this code line to understand normalised_data = (data - min(data))/(max(data) - min(data)). What happens here is that the feature map stack focuses on some features (pixel clusters) so specifically, they have an extremely large value, so when normalisation occurs, their value becomes very small, going towards 0, leading to max_imag being mostly black/dark, now to figure out the same for min_images. Min_images are mostly white, and they are like a negative version of the max_images, the same features that were highlighted as white in the max_images, are highlighted as dark in the min_images. So how does this happen? Min_image arrays will be have very small max and mins (highly negative) so subtracting anything with min would make it bigger, while the features with high values… would have to be pretty negative if they are gonna be black. Wait but why. I am confused, but I dont want to spend more time on this at the moment, but this definitely warrants a thorough investigation. Right now I am thinking about how I want to take a single feature map off the stack and analyse it visually, and also see the distribution of a single pixel across the entire stack. Implementing Motion supervision loss

Implementing the motion supervised loss was fairly straightforward, but ofcourse I made some … choices to uncomplicate the function. For starters when I read the paper it said that patch should consist of all the points at distance less than r1 from p, I assumed that this was talking about the Euclidean distance from p, and I would have to calculate all the points that speicfy that criteria and loop over them, which seemed computationally inefficient, and a pain to implement, so I opted to instead think of the patch as a circle inscribed inside the square I am able to use the corners of the square to easily implement a double for loop getting all the required points. I am probably adding a few extra points because of this method but that is fine, wouldnt make much of a difference. For some reson I assumed that jax would not have a function to resize a n-channel feature map stack via bilnear interpolation, and I set off to implement my own. I was too excited to get results to study bilinear interpolation and implement it from scratch, so I used someone’s code from GitHub (Dont remember who, but i remember seeing a MIT license), but then soon after I realized that jax.image.resize works for any number of channels, so used that one instead. To stop gradient flow from first term, I really didnt know what to do. My first thought was that I should implement the loss function such that the first term is treated as a constant, but the gradient of the second term is appropriately influenced by the value of the first term. However, that proved to be a vain effort. So, not wanting to scour hundreds of pages of documentation, I googled what decorator/function would help with this, but then the AI overview popped up, and told me to use jax.lax.stop_gradient. Since the surprise was alreaady spoiled for me, I went ahead and used this to get the job done. And yes, the authors said that they used bilinear interpolation to get f(q+d), since d is a float. That did not make sense to me at first so I simply used the sign of d, to get q + d, which feels like a fair approximation to bilinear approximation now that I have learnt it. Ofcourse I have also changed the implementation to actually use bilinear interpolation now. Another thing I want to point out is that the standard way you compute gradients in jax/flax is that you wrap your loss-computing function in the grad function, and use that to get the grads. Actually loss-computing function is wrong, more like the forward pass, as typical backprop requires recording of all the operations executed to get the output, and then the loss computation. So I wrote a method called get_dltatent_loss (Yes the naming is contradictory to what I just said, I will change it) to take dlatents (w_code) as an argument, (among other things) and compute the motion supervision loss. At this point I did not implement the mask loss, even the motion supervision patch loss was implemented only for a single point. The StyleGan generator network has been instantiated as an attribute of the DragGan model, so there is no requirement to pass it in arguments. I then used the gradients to update the dlatents, finishing the optimisation step implemntation as well

Implementaion of point tracking

Implementing this algorithm was easy, its simply a nearest neighbours search, but it was excpetionally slow. Like the motion supervision loss, I initially implemented the point tracking algorithm with a naive double for loop. Another thing that confused me was whether I should recompue/ reassign the value of F’ with eah iteration. Ofcourse I was already computing the feature map in motion supervision loss step, so I would simply assign it as a attribute of the model and re-use it in the point tracking step, but that threw a tracing error as motion supervision was being used in grads, so I instead returned it as an auxiallary data, and then assigned it outside of the gradient step. I made a few errors, such as forgetting about the batch dimension in the zero axis leading to confusing results (jax does not throw ‘index out of bound’ errors so one has to careful in how they index). Anyways, since the paper did not elaborate on whether to recompute F’ or reuse the first feature map computed, I decided to use the official implementation as reference. However, since I did not want to look at the code (As part of the constraints), I instead asked gemini to scan the offical codebase, and answer this question. It told me to recompute F’everytime, I asked it to verify and the answer was the same. However, later when I asked Claude the same question, it told me to reuse, and didnt move from its stand even after I pushed back (yayy no sycophancy). Perhaps it was my own bias for less computatin, but the latter seemed correct to me logically, so I went with that. Further more, I realised I dont need to pass the whole feature map, but rather only he values of feature map at the point(s) p, so I did just that, and viola, the entire algorithm is complete. Putting together the loop was a trivial step, so I won’t outline it separately.

Debugging and Improving Performance

After trying out the DragGAN for a few iteration on my pc, the speed seemed supbar (For a cpu that is), so I chose to focus on quality first. The first issue I noticed was that while doing a pointwise manipulation on an image of a man, (the pointwise manipulation was to drag the smile down) the style specific attributes such as age, face structure, beard density were changing as well. As I tried to figure this out, I realised that the authors had mentioned that the work in W+ space, which I had not accounted for in my algorithm. To put it more simply, the disentangled latents work as style embeddings in each convolutional layer of StyleGan’s generator. So in case of StyleGan2, there are 18 convolutional layers, and we would inject the dlatent code into each layer. The authors suggest that when updating the dlatent code, you should only update it for the first 6 layers, as they change more low-level attributes, while the later layers are more responsible for the style specific attributes. So I implemented that by discarding the updates to the later layers in the optimisation step. This one change helped quite a lot, the stylegan now accurately performs point-wise manipulation. I do notice artifacts, disfigurations and warps coming sometimes. For the time-being I will extend the algorithm to work for multiple points.

After adding that capability, I noticed a massive drop in speed, even in GPU. I tried using vmap as well, to vectorize the calculation for a single point to fit all points, but that just made it slower imo. Here I was confused, so I asked how to speed up the algorithm in gemini. It pointed out that for loops are not really gpu optimisedm so then I rewrote the algorithm, for both motion supervision and point tracking to leverage a 3d grid of shape (2r+1)x(2r+1)x(n_points), and perform all required calculations on this 3d grid. It worked beautifully, the speed increased by ~150%. The next thing I did was reimplement the StyleGan code, as I had mentioned I would do earlier. So what I did was analyse the shapes of the weights given in the h5 files by matthias wright, and also analysed his code, and implemented my own variant in flax.nnx. I followed a specific pattern for implementing the Mapping Network and Synthesis Layer. The remaining models were pretty much the same as in linen, so I just asked Gemini to generate this code in the same pattern as mine. This re-implemntation allowed me to get rid of a bunch of if statements and conditionals in the code, and I also leanred about truncation_psi. Apparently, it is a way to curb the presence of artifacts and disfiguratins in the image by moving the disentangled code produced by the mapping network more towards the average. After using this, I noticed a drop in disfiguration and artifacts in generated images.

Implementation of Mask Loss

This was fairly straightforward, I delegated the task of building the gui for drawing a mask to Gemini, while I implemented the mask loss. The authors specify using L1 norm, which I do use, over the last axis. After which I take the sum of the norm, multiply it by lambda=20, and add it to the motion supervision loss. My only concern was that mask loss was too big a value, but when I used mean instead of sum, it was like the mask loss played no effect on thegraidents. So instead I divided the sum by the sum(1-mask), so its the sum of the actual values that are allowed to pass through. This seemed to work

Experiments and failure mode analysis

I performed a lot of experiments, and observed some failure modes, and identified some areras of potential improvement, that I will explore soon. First of all, the author’s heuristic on taking the 6th block for feature map and updating the first 6 layers of W+ seems flaky to me. It might be the most consistent in performance across datasets, but there has got to be a way to find the correct feature map when working on a specific feature, and I think the same can be applied for point tracking, because point tracking is failing badly. When I checked the progress of a single image at each iteration, I noticed that the handle point keep drifting away while the actual feature that it is supposed to be tracking has not moved as much. I wonder if there is something wrong with my implementation though, but I validated everything. I even gave my finished code to Claude and Gemini, gave them the official repositories, and check if my code had any mismatch or faults. Nothing of merit was found in their analysis. I tried adding an outward-increasing weightage to the distances grid in point tracking, but that did not seem to help much. Updaying the reference points (old points) via exponential averaging helped a bit, giving a large weight like 0.95 to the original points, so the algorithm didnt lose its structure. I wonder if I can combine the weightage approach and updating of reference points. I also see that sometimes there are bad updates, which could be characterized as very large updates causing overshooting, making the resulting image warbled. When I had compared my code with source code via CLaude, it said that the official implementation used a regularisation loss to where it checked how far the new w_code is from the old w_code. Not sure how that helps, maybe its to make sure the image stays on the manifold, or to prevent large updates. I wonder if we can pin-point the locality of the updates to the w_code, since it is disentangled it should be possible. I will try perform pointwise manipulation on the same image with different truncation_psi’s to see how that affects. Update: Nothing worthwile to note.

Heads up, I just discovered that the point tracking failure is an actual problem faced by multiple people, and there have been follow up papers to improve on this. The good part is that I was close with how I was trying to fix it, some paper called FreeDrag also updated the reference point via a sort of exponential average, but the weight coefficient is dynamically computed at each iteration, and depends on the value of the loss. They also enforce point tracking to only pick points along the 1d line between the taget point and handle point which is smart, dont just look at closer points, make a much tighter constraint. Let me see if there is anything else I can do to improve the point tracking algorithm. For the time being, my focus will be on getting experiments to showcase, and improving the speed of the algorithm.
